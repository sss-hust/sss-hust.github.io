## MLA

先学习下MLA，下图可以看到Rope的用法与MHA不同，传统的是将token中每两个维度进行一次旋转，由于旋转矩阵是正交矩阵，不会改变其模（数学原理还是蛮复杂，掌握不了），然后对整个token来说，是在高维空间进行旋转，并且随着维度增大，旋转的越来越慢，从如下公式可见（i表示token中第几对），用R与(x,y)相乘就得到旋转向量，后续做注意力计算时，这部分会变成复数的角度运算，简洁明了的表示相关位置。

$$
R(\theta)=\begin{bmatrix}\cos\theta&-\sin\theta\\\sin\theta&\cos\theta\end{bmatrix}
$$

$$
\theta_i=position\times base^{-2i/d}
$$

![20260314205650546.png](20260314205650546.png)

MLA核心是减轻KVcache的负担，因此对QK进行了降维（KV共用一个潜向量），这样KVcache中只需要存储这个以及其对应得位置向量就可以，位置向量在MLA中使用的是头尾相连，并没有直接加入到特征向量中。此外，在decode阶段，用矩阵融合进一步减少访存，q的升维与k的升维矩阵可以在加载时就相乘，同时v的升维矩阵与o的矩阵也进行相乘（这里稍微扩大了存储量，细节后续再梳理）。

## MLA内核优化

比赛针对的是decode阶段，因此我们重点关注从内存中读取kvcache，如下，qlen非常短（有长度为4的是为了检测是否满足变长注意力机制），但是kvlen非常长，主要时间可能是花费在读取数据中。

```python
benchmarks:
  # bs=4, tp=4
  - {"batchsize": 4, "qseqlen": 1, "kvseqlen": 1024, "tp": 4, "seed": 4237}
  - {"batchsize": 4, "qseqlen": 4, "kvseqlen": 8192, "tp": 4, "seed": 4251}
  # bs=32, tp=8
  - {"batchsize": 32, "qseqlen": 1, "kvseqlen": 8192, "tp": 8, "seed": 5415}
  - {"batchsize": 32, "qseqlen": 4, "kvseqlen": 1024, "tp": 8, "seed": 5420}
  # bs=32, tp=4
  - {"batchsize": 32, "qseqlen": 1, "kvseqlen": 1024, "tp": 4, "seed": 5432}
  - {"batchsize": 32, "qseqlen": 4, "kvseqlen": 8192, "tp": 4, "seed": 5443}
  # bs=128, tp=8
  - {"batchsize": 128, "qseqlen": 1, "kvseqlen": 8192, "tp": 8, "seed": 7816}
  - {"batchsize": 128, "qseqlen": 4, "kvseqlen": 8192, "tp": 8, "seed": 7824}
```

我们的任务非常集中，输入是已经计算好的Q，只需要读取对应KV计算出结果就可以，后续任务不用考虑。

基线给的逻辑如下：

```
整理输入
从cache中读取fp8的k
量化q到fp8
按照批次串行访问每一批次：
    读取对应q，k
    调用底层scaled_mm计算注意力分数
    读取fp16的v
    计算最终稿结果并写回
返回结果
```

从上可以看出，最大的优化有亮点，一是将串行改为并行，二读取的v也采用低精度

先把串行改为并行，由于多批次存在，天然适合采用多线程进行计算，采用triton进行优化，最终结果如下，可以看到短kv算的比较快，长的话时间就激增了，比赛放允许针对特定算子进行优化，因此可以根据测试样例去调整tiling的比例。距离前十还需要提速十倍！同时batch的增大对时间影响极小

![20260315152617854.png](20260315152617854.png)

上述优化方法主要思想是利用GPU的并行能力，将需要做的矩阵乘法拆成一小块并行去做，例如将输入的q逻辑上将token与head维度进行合并，然后每个block处理其中一块，再根据flashatten的思想，对每个q行快，将k也拆成多个行块，采用迭代更新的方法计算attention分数，同时在qk相乘内部对k再次进行列分块，确保每个矩阵都可以在SRAM级别完成运算，减少HBM的读取，最终算出的结果与v相乘就不继续列分块了，直接得到最终的行块。

主要优化在串行变并行了，同时利用SM内部存储减少外部内存读取次数。

后续优化考虑针对特定数据设置特定tiling（不清楚底层会怎么分配，可能比较吃力，但ai可以力大砖飞）、v进行量化后传入kernel（减轻寄存器压力，提高活跃线程块比例）。

与满血版gemini 3.1对话，发现当前SM利用率可能不高，因为每次只有一个token，头一般是16或者32，这样的话只会创建一个block，导致大部分算力浪费，尤其是在block内部计算。先把这部分进行优化，最后再优化。

## subv5 220us

版本比较混乱了 ，主要原因是中间尝试了下MXFP4，但是发现反量化比较复杂，导致了需要大量计算，变成了计算受限，可能是反量化的思路不对。

现在打算继续优化FP8，看了下GPU优化相应知识，发现之前没有用上TMA这个大杀器，本版本使用上后，优化了大概14%，同时存在一些微小指令未合并（比如将k分两个部分读），最后的写入也没有采取TMA方式，还存在微小优化空间。但是现在我要像专业的分析师一样去分析了，一步步找到瓶颈。

首先是分析硬件瓶颈，MI355X在官网上的信息提供的是MXFP4峰值性能为10.1PFLOPs（硬件原生支持），未稀疏化的FP8为5PFLOPs，稀疏化的FP8为10.1FLOPs（2：4稀疏化指四个数值里会有两个0，硬件可以原生跳过），FP16/BF16都是2.5PF/5PF。同时具有256个CU（即SM），每个CU具有4个matrix core（tensor core），64个SP。L2cache大小为256MB，带宽未给。HBM大小为288G，带宽8TB/s，没有给L1相关数据。

[CDNA4 Instruction Set Architecture: Reference Guide](https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/instruction-set-architectures/amd-instinct-cdna4-instruction-set-architecture.pdf)在这里有具体数据，L1cache大小为160KB，分为64个bank，每个bank有640个4B条目，同时有256 * 4B的寄存器，每个CU都有两个这么多寄存器，一个负责计算暂存、一个负责读取暂存。

如下是gemini帮我在网络上搜索的，接下来的优化思路先仿照[手写 CUDA GEMM，性能达到 cuBLAS 的 99.9% - 知乎](https://zhuanlan.zhihu.com/p/2017644542644486877?share_code=TNU4pccxo7Yr&utm_psn=2017973792954139837)进行

## 回归

![20260330164357478.png](20260330164357478.png)

由于中途导师喊去北京，耽搁了一周时间，回来发现task有变化，原先seq_q的长度有1有4，现在只有1了，但最大batch涨到了256，需要更直面存储墙了。整个问题非常简单，抽象成就是[batch,head_num,head_dim] @ [seq_len,head_dim].T@[seq_len,head_dim]，每个batch对应的的kvcache不一样，一个token就要和最长8192个token做注意力计算，这里读取存在较大的问题。

落实到具体的数据中，除了上图的数据，还有head_q_num = 16，kv头数为1，qkhead_dim为512维，额外加上64维的位置嵌入，而v就只有512维。

MI355X的硬件要素为288G的显存，256MB的L2cache，160KB的L1cache。其余如下图：![20260330165727026.png](20260330165727026.png)

如果想要把一个k的前512维放进GPU，需要4G空间，对于MI355X只能放进HBM中，何况这只是一个批次，还有大量的资源需要放进GPU中，因此得想办法让读取尽可能快（显而易见不可能是计算瓶颈，因为读一个字节才算两次）。

v1版本实现的是基础的online-softmax，对每一个batch里的每64行启用一个block，一个block就处理64行v乘以全长的kv，同时乘以k时先按行分块，行块内部再按列分，减轻存储压力，q与k行块相乘后得到结果再与相同的大小的行块相乘，得到暂时的O，后续每个行块依次更新。不足之处在于需要维护一个$64*512*4=128KB$的acc结果，块并行做的并不好。于是v1.1尝试分成两阶段，第一阶段不涉及v，只更新行最大值，第二阶段对v分块，计算o，效果平平，缓存命中率比较低，同时也没有减少读取kv的次数。v1.2加入tiling参数自动搜索，选择最优的情况。300+us

v2版本目的在于解决kv过长导致每个block负载较大，无法较好的并行完成，于是采用splict kv的思路，将kv分块，同时引入一个并行维度，第一个kernel中每部分head和部分kv进行计算，这里依旧沿用前面的思路，kv分开来，都进行列分块。第二个kernel就是把前面每个chunk的信息进行更新，时间上并没有多大优势，300+us。

v3版本读取的v采用fp8格式，前面采用的是fp16，访存减半（但时间没有减半，只减少了50us），反量化只需要乘以标量，简直是白嫖的福利，同时把循环不变量直接提取到最外面，减少计算指令。275us。

v4系列版本尝试了下mxfp4，访存是再次砍半了，但是反量化很头痛。4.1版本直接使用基础定义反量化，4.2使用LUT分支折叠查找表，一串where判断符号位，通过编译将其变为高效指令，这样就可以直接得出结果。理想是美好的，现实是骨感的，时间来到ms级别，反量化太吃时间了。

这里再补充下AMD的硬件架构，每个CU有四个SIMD单元，其中有64个管道，一个线程就运行再一个管道中，wave运行再SIMD上，即物理和逻辑概念。

在看了[高性能矩阵乘法内核解剖](https://www.aleksagordic.com/blog/matmul?trk=public_post_comment-text)后，使用v5版本尝试TMA，异步加载数据，同时将k的块常驻在寄存器里，这样后面v的计算就可以不用再次读取了，但是这样一个wave就需要190个寄存器坑位，一个SIMD单元只有256个，就很尴尬了，只能同时跑一个，硬件上限是32，并行程度就比较低了。具体计算过程如下：

```
MI355X CDNA4 寄存器预算 (per wavefront):
  256 VGPR × 4B = 1024B/lane × 64 lanes    → 用于 KV tile, Q, P, masks
  256 AccVGPR × 4B = 1024B/lane × 64 lanes → 用于 acc, qk (MFMA 累加器)
  LDS: 160KB/CU (可用于溢出/预取)

寄存器分配 (BLOCK_M=16, BLOCK_N=64):
  kv_lora fp8   [64, 512]: 32768B / 256B/vgpr = 128 VGPRs
  kv_rope fp8   [64, 64]:  4096B / 256        = 16  VGPRs
  q_lora  fp8   [16, 512]: 8192B / 256        = 32  VGPRs  (hoisted)
  q_rope  fp8   [16, 64]:  1024B / 256        = 4   VGPRs  (hoisted)
  masks, scales, etc.                         ≈ 10  VGPRs
  ───────────────────────────────────────────────────────────
  Total VGPR                                  ≈ 190 / 256  ✓

  qk      fp32 [16, 64]: 4096B / 256         = 16 AccVGPRs
  acc     fp32 [16, 512]: 32768B / 256        = 128 AccVGPRs
  m_i, l_i     [16]:                          ≈ 2  (in VGPR)
  ───────────────────────────────────────────────────────────
  Total AccVGPR                               ≈ 144 / 256  ✓
```

虽然并行度没有多大，但由于计算量没有多大，比起之前的还是存在一定的优势，因此时间降到了224us。v5.1在这个基础上针对不同的样例做了优化，当head数为32时，block_m为16，就会发两个block，但是两个读取的kvcache是同样的，造成资源浪费，因此在依次循环中将其解决。同时将最后的写回也使用TMA，中间由于make_block_ptr需要是二的倍数，因此把k分成两部分加载。

v6在v5基础上引入split kv，对于长kvcache增加并行度，但由于可能运行在不同的CU上，因此需要全局规约，把结果存在HBM中，后期再用pytorch端合并，即使人为的增加了读取量，但由于并行度上去了，长kccache效果不错。v7则是针对短cache，由于之前是在kernel外部量化Q，引入了一些lauch开销，因此这里选择不把Q量化，直接使用，由于Q本身很短，对于读取来说并没有什么影响，但使用fp16后对应的矩阵乘法只能使用2.5PF的FP16了，虽然计算能力减半，但对于memory bond不影响什么。这里取消了split kv，专注于短cache的优化。

v8结合前面的优势，同时优化v6中reduce使用pytorch的弊端，使用专门的kernel进行规约，同时加入智能门控机制，并行度不够就切kv，否则直接全量上。v9大胆开启深层流水，因为accvgpr是单独的256个，完全可以大胆使用，同时block数也可以变大，时间来到196us。9.1则是发现python端消耗比较大，因为我们精准计算每个batch有多少个token需要使用item，就会打断GPU上的流水，减去后短序列场景收益60%，长序列收益20%。最后9.2让所有序列都根据负载情况去判断是否需要开启split kv，进一步激发短序列潜力，收敛至最优。

后续就在致力于改进长kccache场景表现，计算发现长序列场景下kv切的粒度还是太大了，导致每个SIMD一次只能跑一个wave，于是加大刀法，长序列也开始收敛。整体最终停留在60us，距离前排差距一倍，工作进度落后10天。
